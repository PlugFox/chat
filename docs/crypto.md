# Cryptography

> Status: **agreed** (2026-10-25). This is the specification `crates/crypto`
> is written against. Still open: the HPKE crate ([Crate choice](#crate-choice)).
> Every change to a format bumps its version and is reviewed like code.

Read [threat-model.md](threat-model.md) first: it says what this design
protects and what it does not.

## Rules

1. Primitives come from maintained, preferably audited crates. We compose
   them; we never implement a primitive.
2. One Rust crate, `crates/crypto`, implements every format and operation. It
   compiles natively (server, tests, tools) and to `wasm32-unknown-unknown`
   (client Web Worker). The client never reimplements a format in TypeScript.
3. Every binary format starts with a version byte. A reader rejects versions
   it does not know; it never guesses.
4. Every ciphertext is bound to its place by AAD (owner, scope, key version,
   kind, position). Every key derivation has a unique label.
5. Secrets are zeroized on drop (`zeroize`), compared in constant time
   (`subtle`), and never implement `Debug`/`Display` with their content.
6. Randomness comes from the OS (`getrandom`; in WASM via
   `crypto.getRandomValues`). Tests inject a seeded RNG to produce vectors.

## Suite v1

| Purpose | Primitive | Crate (to confirm in review) |
| ------- | --------- | ---------------------------- |
| Public-key encryption of records | HPKE, RFC 9180: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 (suite `0x0020/0x0001/0x0003`) | `hpke` (rozbb) or `hpke-rs` (Cryspen) — see [Crate choice](#crate-choice) |
| Symmetric key wrapping | XChaCha20-Poly1305, random 192-bit nonce | `chacha20poly1305` (RustCrypto; NCC Group audit) |
| File streams | STREAM over XChaCha20-Poly1305, 64 KiB chunks | `chacha20poly1305` |
| Key derivation | HKDF-SHA256 | `hkdf`, `sha2` |
| Passphrase (not in v1) | Argon2id | `argon2` |
| Link-request MAC | HMAC-SHA256 | `hmac` |
| Local device key | AES-256-GCM, non-extractable WebCrypto key | browser WebCrypto (the only place a non-extractable key exists) |

### Crate choice

The brief asks for audited crates. The honest state, to verify before the
first crypto PR:

- `chacha20poly1305`, `hkdf`, `sha2`, `x25519-dalek`: RustCrypto / dalek,
  widely used, with public audits of the AEAD and curve code.
- `hpke` (rozbb): the most used Rust HPKE; **not formally audited** (a
  Cloudflare internal review of an early version). Pulls the RustCrypto stack
  we already use.
- `hpke-rs` (Cryspen): pluggable backends; the `libcrux` backend has formally
  verified primitives, the RustCrypto backend matches the rest.

Proposal: prototype both behind a thin internal `seal`/`open` API, run the
RFC 9180 test vectors natively and in WASM, compare WASM size and dependency
tree, then pick one and record why here. HPKE is a small composition over the
audited primitives above; our own vectors and property tests cover it either
way.

## Identifiers and encoding

- `user_id`, `scope_id`, `wrap_id`, `file_id`, `entry_id`: UUIDv7, 16 bytes
  in binary formats.
- `key_version`, `message_id`, `chunk_index`: `u32`, big-endian.
- Periods: `i64` seconds since the Unix epoch (UTC), big-endian, plus a
  `u8` granularity (day, hour, instant) where the register kind needs it.
- Binary blobs are stored as `BYTEA` and travel in JSON as unpadded
  base64url.
- Variable-length fields inside AAD and labels are length-prefixed (`u16`
  BE), so no two field lists encode to the same bytes.
- Labels are ASCII, prefixed `vc/v1/`. Below, `||` is concatenation and
  `lp(x)` is the length-prefixed encoding.

## Key hierarchy

```
unlock secret (passkey PRF output | recovery secret | passphrase)
   └─ HKDF → KEK ──wraps──▶ ARK (256-bit, random, per account)
                              ├─ HKDF "vc/v1/scope-wrap"   → scope wrapping key ──wraps──▶ scope private keys
                              ├─ HKDF "vc/v1/commitment"   → ARK commitment (stored, public)
                              └─ HKDF "vc/v1/writer"       → writer X25519 key (authenticates client-written records)
scope key pair (X25519, random, per scope and key version)
   └─ public key ◀──sealed to── records, file content keys
```

### Account Root Key (ARK)

32 random bytes generated by the first client at key setup. It exists in
plaintext only inside the client Web Worker. Derived keys:

```
k_scope_wrap  = HKDF-SHA256(ikm = ARK, salt = "", info = "vc/v1/scope-wrap"  || user_id, L = 32)
commitment    = HKDF-SHA256(ikm = ARK, salt = "", info = "vc/v1/commitment"  || user_id, L = 32)
writer_secret = HKDF-SHA256(ikm = ARK, salt = "", info = "vc/v1/writer"      || user_id, L = 32)
```

The server stores `commitment`. A client that obtained an ARK by any route
(unwrap, recovery, linking) recomputes it and refuses an ARK that does not
match: a wrong key fails loudly instead of producing garbage later.

### ARK wraps

One wrap per unlock method, stored on the server, returned only to an
authenticated session of the same user.

```
wrap = v=1 (u8) || method (u8) || wrap_id (16) || method_params || nonce (24) || ciphertext (32 + 16)
aad  = "vc/v1/ark-wrap" || user_id || wrap_id || method
```

| Method | `method` | KEK input | `method_params` |
| ------ | -------- | --------- | --------------- |
| Passkey PRF | 1 | 32-byte PRF output for `prf_salt` | `credential_id` (lp), `prf_salt` (32) |
| Recovery key | 2 | recovery entropy (16 bytes, see below) | — |
| Passphrase (later) | 3 | Argon2id(passphrase, salt, m, t, p) | `salt` (16), `m`, `t`, `p` (u32 each) |

```
KEK = HKDF-SHA256(ikm = input, salt = wrap_id, info = "vc/v1/kek/" || method || user_id, L = 32)
```

**Passkey PRF.** At registration the client asks for the `prf` extension;
the PRF is evaluated (during registration where the authenticator supports
it, otherwise with an immediate assertion) with a random 32-byte `prf_salt`
stored in the wrap. Each passkey has its own salt and wrap. Synced passkeys
(iCloud Keychain, Google Password Manager) return the same PRF output on every
synced device, which is what makes "unlock on a second device" work without
linking. Authenticators that do not return PRF output cannot hold a wrap; the
client says so and falls back to the recovery key.

**Recovery key.** 128 random bits (brute force is out of reach; the wrap is
not password-like), shown once at key setup as **12 words from the BIP-39
English word list** with its 4-bit checksum, and confirmed by typing some of
the words back. The English list is used in every UI language: one list keeps
the key portable between locales, and the words are short and distinct. Input
is case-insensitive, accepts any whitespace, and offers completion from the
list; a wrong checksum is reported before any unwrap is attempted. The KEK
input is the 16 bytes of entropy, not the BIP-39 seed (no PBKDF2 stretching is
needed for a random 128-bit secret). The client never stores it; the server
never sees it.

**Passphrase.** Not in v1 ([threat-model.md](threat-model.md#non-guarantees),
N7): the operator can guess it offline. If added, Argon2id parameters are
stored per wrap so they can be raised, and the client enforces a strength
gate.

### Scope keys

Each scope has an X25519 key pair per `key_version` (starting at 1). Scope
keys are random, not derived from the ARK, so that ARK rotation re-wraps them
without re-encrypting data, and one scope can be rotated alone.

```
public key              stored in plaintext, readable by anyone allowed to write to the scope
wrapped private key     = v=1 || nonce (24) || XChaCha20-Poly1305(k_scope_wrap, nonce, sk, aad)
aad                     = "vc/v1/scope-key" || user_id || scope_id || key_version
```

Creating a scope (a new chat, notebook, register) therefore needs an unlocked
client: it generates the pair and uploads the public key with the wrapped
private key. The server, importers and the agent can **write** to existing
scopes only.

### Scope kinds

| Kind | Instances | Holds |
| ---- | --------- | ----- |
| `settings` | 1 | LLM provider configs, preferences |
| `audit` | 1 | access-log reasons |
| `profile:<group>` | a few fixed groups | user characteristics |
| `chat` | one per chat | chat title, messages, tool results, summaries |
| `notes` | one per notebook | notebook name, note titles and bodies |
| `register` | one per register | register values |
| `files` | per notebook / chat (later) | file content keys |

`profile` uses fixed groups that match how a grant is phrased, so one grant
does not reveal medical data when the agent only needs height:

| Scope | Attributes |
| ----- | ---------- |
| `profile:basics` | age (birth date), sex, height |
| `profile:medical` | allergies, conditions, medications |
| `profile:lifestyle` | diet, activity level, goals |

Moving an attribute to another group means re-sealing it to that group's key.

## Records

A record is any encrypted value: a message, a title, a note body, a register
value, a setting, an access-log reason, a file content key.

```
record = v=1 (u8) || mode (u8) || key_version (u32) || enc (32) || ciphertext
```

- `mode` = 0: HPKE base mode, any writer (server, importers).
  `mode` = 1: HPKE auth mode with the user's writer key: written by one of the
  user's clients ([Authenticity](#authenticity)).
- `enc` is the HPKE encapsulated key; `ciphertext` is HPKE single-shot
  `Seal(pkR = scope public key[key_version], info, aad, padded plaintext)`.
- `info = "vc/v1/record/" || kind`.
- `aad = "vc/v1/record" || user_id || scope_id || key_version || kind || kind_fields`.

| `kind` | `kind_fields` (bound by AAD) |
| ------ | ---------------------------- |
| `chat.title` | — |
| `chat.message` | `message_id` (u32), `author` (u8: user, assistant, tool, summary) |
| `notebook.name` | `notebook_id` |
| `note.title`, `note.body` | `note_id` |
| `register.value` | `entry_id`, `period_start` (i64), `granularity` (u8) |
| `profile.value` | `attribute` (lp) |
| `settings.value` | `key` (lp) |
| `audit.reason` | `log_entry_id` |
| `file.key` | `file_id` |

Binding `period_start` matters: periods are plaintext for range queries, and
without the binding the server could move a weight value to another date.

Cost: one X25519 operation per record to open. A 64-message page is ~64
operations; a year of daily steps is ~365. Both are milliseconds in WASM.
If register histories grow large, a per-scope batch format (one HPKE context,
many values) can be added as a new kind.

### Padding

Ciphertext length is metadata. Plaintext is framed and padded before sealing:

```
padded = len (u32 BE) || plaintext || zeros up to Padmé(4 + len), minimum 64 bytes
```

Padmé (Nikitin et al., PETS 2019) leaks O(log log n) bits of the length with
at most ~12% overhead. The reader checks that the padding bytes are zero.

### Authenticity

HPKE base mode lets anyone with the public key write a record, including the
server ([threat-model.md](threat-model.md), N3). So from v1, records written by
the client use HPKE **auth mode** with a writer key pair derived from the ARK
(`writer_secret` above; the public key is stored on the server):

- A `mode = 1` record that opens was written by one of the user's clients: the
  server cannot forge or alter it.
- `mode = 0` records (assistant replies, tool results, summaries, imports) are
  shown as server-written. A reader never accepts `mode = 0` for a kind only
  the client writes (`chat.message` with `author = user`, `note.*`,
  `notebook.name`, `chat.title`, `profile.value`, `settings.value`, and
  `register.value` entered by hand), so the server cannot downgrade a record.
- It gives neither freshness nor completeness (N4).
- Holding a scope private key also allows forging auth-mode records to that
  scope (HPKE key-compromise impersonation); both keys live only in the client.

## Files (after v1)

```
header  = v=1 || file_id (16) || chunk_size (u32) || nonce_prefix (19)
chunk_i = XChaCha20-Poly1305(content_key, nonce = nonce_prefix || i (u32 BE) || last (u8), chunk, aad = header)
```

STREAM construction: the counter prevents reordering, the last-chunk flag
prevents truncation, the header in AAD binds every chunk to its file. The
32-byte `content_key` is random per file and stored as a `file.key` record in
the owning scope. Chunks are 64 KiB of plaintext.

## Unlock and devices

### First key setup

1. The user signs in (identity: Google or email OTP).
2. The client generates the ARK, registers a passkey with PRF, computes the
   PRF wrap, generates the recovery key and its wrap, generates key pairs for
   `settings`, `audit` and the profile scopes.
3. The client shows the recovery key and asks the user to confirm it.
4. Only then does it upload: wraps, commitment, writer public key, scope public
   keys and wrapped private keys, in one transaction. A setup interrupted
   before step 4 leaves nothing on the server.

### Unlock

Sign-in gives a session; unlock gives keys. The client fetches the wraps,
uses one method to get the KEK, unwraps the ARK, checks the commitment, and
then fetches and unwraps scope private keys lazily as scopes are opened.

### Device linking

A new device gets the ARK from an already unlocked device. The server relays
messages and must not be able to substitute keys, so a secret travels only
through the QR code, which the server never sees. The QR is a URL whose
parameters are in the fragment (`https://host/link#…`), so a phone camera app
can open it and the fragment is never sent in an HTTP request.

Common: the server creates a link session (`sid`, 2-minute TTL, single use,
bound to the user's account). `k` is 32 random bytes generated by the device
that shows the QR.

**A. New device shows the QR, unlocked device scans** (desktop shows, phone
scans):

1. New device N generates an ephemeral X25519 pair; QR = `sid`, `pk_N`, `k`.
2. Unlocked device U scans it, asks the user to confirm, and sends
   `HPKE.Seal(mode = psk, pkR = pk_N, psk = k, psk_id = sid, info = "vc/v1/link", aad = user_id || sid, pt = ARK)`.
3. N opens it and checks the commitment.

`pk_N` reaches U through the camera, so the server cannot replace it; the PSK
proves to N that the sender saw the QR.

**B. Unlocked device shows the QR, new device scans** (phone shows, laptop
with a camera scans, or the user types a short code — later):

1. U shows QR = `sid`, `k`.
2. N generates an ephemeral pair and sends `pk_N`, `tag = HMAC-SHA256(k, "vc/v1/link-request" || sid || pk_N)`.
3. U verifies `tag` (the server does not know `k`, so it cannot inject its own
   `pk_N`), asks the user to confirm, then seals as in A.2.

Either way the server sees `sid`, `pk_N` and an HPKE ciphertext only.

### Remember this device

Optional. The worker generates a non-extractable AES-256-GCM key with
WebCrypto, stores it in IndexedDB, and stores
`AES-GCM(device_key, nonce, ARK, aad = "vc/v1/device" || user_id)` next to it.
Nothing is uploaded except a device record for the device list. Signing out
or "forget this device" deletes both. Trade-off: [threat-model.md](threat-model.md), N6.

## Rotation (after v1)

- **Scope key rotation**: generate `key_version + 1`, write new records with
  it, re-encrypt existing records on the client, then delete the old wrapped
  private key. Records carry `key_version`, so mixed states are readable.
- **ARK rotation**: new ARK, re-wrap every scope private key, new wraps for
  every unlock method. Each passkey has to be present to produce a new PRF
  wrap, so rotation also re-enrolls passkeys; missing ones are dropped.

## Client worker API

The WASM module runs in a dedicated Web Worker. The main thread talks to it
through a narrow, typed message API and never receives key material:

| Call | Does |
| ---- | ---- |
| `setup(...)` | First key setup; returns the upload bundle |
| `unlock(method, material)` / `lock()` | Unwrap the ARK / wipe all keys |
| `link.offer()`, `link.accept(...)` | Device linking, both directions |
| `scope.create(kind)` | New key pair; returns public key + wrapped private key |
| `seal(scope, kind, fields, plaintext)` | Returns a record |
| `open(scope, kind, fields, record)` | Returns plaintext |
| `grant.export(scopes, query)` | Decrypts what a permission request asked for |

There is no call that returns the ARK, a KEK or a scope private key.

## Testing

- **Vectors**: `crates/crypto/vectors/*.json`, produced with a seeded RNG,
  committed, and checked natively and in WASM by the same test list. RFC 9180
  vectors for the chosen suite run too.
- **Property tests** (`proptest`): seal/open round trips for every kind;
  flipping any bit of the record, the AAD fields, the scope or the key version
  fails; wrong padding fails.
- **Fuzzing** (`cargo fuzz`): every decoder (`record`, `wrap`, link messages,
  file header) on arbitrary input must return an error, never panic.
- **Review**: changes under `crates/crypto` or this page go through the
  `crypto-review` skill and a human review.
